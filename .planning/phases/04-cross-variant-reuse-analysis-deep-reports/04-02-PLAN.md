<feature>
  <name>Blocker source file and row</name>
  <files>app/services/quality.py, tests/test_quality.py</files>
  <behavior>
    Every object in `blockers()` `sources` gains two keys:

    - `source_file`: `source_file.file_name` for that row's `source_file_id`
    - `source_row`: the integer `source_row` on `engineering_note`, `plm_assembly`, or `erp_material`

    Cases:
    - A note whose text contains both `48V DC` and `24 V`, with `author` `N-064`, `source_row` 64, and a `source_file` named `technical_notes.csv`, produces one `conflicting_evidence` row. `values` is `["24 V DC", "48 V DC"]`. Both source entries carry `source_file` `technical_notes.csv` and `source_row` 64. The explanation still says both values were kept.
    - `PAX-COUNT-MOD-E` with lifecycle `Prototype` and a peer counting assembly with lifecycle `Released` produce `lifecycle_mismatch`. Each source entry carries that assembly row's file name and `source_row`. Values stay `Prototype` and `Released`.
    - An ERP material with `status_raw` `OBSOLETE` produces `erp_lifecycle`. Its single source entry carries that material's file name and `source_row`.
    - A note with one voltage only does not become a conflict.
    - Existing explanations for these three issue types are unchanged.

    If an existing test compares a source dict with exact equality, extend the expected dict with the two new keys in the RED commit. Do not loosen the voltage or lifecycle assertions.
  </behavior>
  <implementation>
    Join `source_file` on `source_file_id` inside the three queries `blockers()` already runs (`engineering_note`, `plm_assembly`, `erp_material`). Copy `file_name` and `source_row` onto each source dict before append.

    Do not add a column. Do not rewrite `technical_fact` beyond the inserts `blockers()` already performs. Do not parse the CSV file from disk.
  </implementation>
</feature>
