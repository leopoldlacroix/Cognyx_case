**Constraining decisions:**
- Follow the canonical BOM rule in `03-CONTEXT.md`. Pending or rejected identity blocks that source component. No identity row means a singleton canonical component.
- Do not require `assembly_reconciliation`. That table is empty. Create assemblies from `source_assembly.normalized_reference`.
- Create variants from `plm_variant.variant_ref_normalized`.
- Functional similarity and variant-specific rows must not merge two normalized references into one component id.
- Accepting an identity cluster (use `decide_reconciliation` from 03-01) then rebuilding the model must place every accepted member's BOM lines on the same `component_id`.
- Rejected mappings must not appear in `bom_relationship`. Unresolved source lines must still be listed in the return value.
- Re-running `build_canonical_model` is idempotent: it replaces derived canonical rows and BOM links for this build rather than duplicating them. Do not delete raw tables, source entities, or reconciliation rows.
- Do not auto-link `MAT-10001` to `CTRL-AIR-01`.
</context>

<feature>
  <name>Canonical BOM propagation</name>
  <files>app/services/canonicalization.py, tests/test_canonicalization.py</files>
  <behavior>
    `build_canonical_model(conn)` returns:

    ```text
    {
      "variants": int,
      "assemblies": int,
      "components": int,
      "bom_relationships": int,
      "unresolved": [{"source_bom_line_id": int, "reason": str}, ...]
    }
    ```

    Cases:
    - A PLM component on two variants, no reconciliation row → one canonical component, two `bom_relationship` rows, unresolved empty for those lines. This is SCEN-A for an already-shared reference.
    - Two source components in one identity cluster, both PENDING → their BOM lines are unresolved with reason `identity_pending`. No `bom_relationship` for them. Other singleton components on other lines still resolve.
    - After both cluster rows are ACCEPTED, rebuild → one shared `component_id` and a BOM row per source line. `variants` count for that component is 2 when the lines are on two variants.
    - One cluster member ACCEPTED and the other still PENDING → only the accepted member's lines are in `bom_relationship`. The pending member's lines stay unresolved.
    - REJECTED identity → that source's lines stay unresolved with reason `identity_rejected` and no canonical id on the reconciliation row.
    - A functional_similarity row between two different refs does not collapse them. Each still gets its own component if it has no identity row.
    - A variant_specific row does not attach that source to another component's id.
    - Quantity and unit on `bom_relationship` come from `quantity_normalized` and `uom_normalized`. `source_bom_line_id` is `plm_bom_line.id`.
    - Second call does not increase `bom_relationships` for the same lines.
    - Quarantine rows are not in `plm_bom_line` and must not be invented as BOM links.

    Tests build rows with SQL. Use `decide_reconciliation` for accept/reject. Do not ingest the full CSV in this plan.
  </behavior>
  <implementation>
    New module `app/services/canonicalization.py`. Clear and refill `variant`, `assembly`, `component`, and `bom_relationship` at the start of a build so reruns stay idempotent. Do not clear reconciliation tables.

    Match PLM BOM component refs to `source_component` on `source_system='PLM'` and `source_reference=component_ref_raw` (extraction stores the raw ref). Use `normalized_reference` only as the canonical name, not as the join key, because several raw refs share one normalized ref inside an identity cluster.

    Leave supplier canonicalization to the same singleton-or-accepted rule if it is cheap, but do not block BOM rows on suppliers.

    Also write `canonical.html` through the same static-page shell as `workflow.html` (`app/services/html_pages.py`). Show accepted identity clusters with their canonical id, and BOM lines still unresolved because identity is pending or rejected. Do not add a web framework.

    Do not edit `app/services/review.py`. A one-line link in the existing nav is enough if `cli.py` must change; prefer adding the page inside `write_site`.
  </implementation>
</feature>
