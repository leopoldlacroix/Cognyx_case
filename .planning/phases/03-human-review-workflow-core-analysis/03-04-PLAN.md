**Constraining decisions:**
- Already reused reads `bom_relationship` only. Pending aliases are not reused until accepted and the model is rebuilt.
- Variant-specific rows are excluded from reusable candidates.
- Do not treat `MAT-10001` as the HVAC controller.
- SCEN-F is not in the Phase 2 hyphen detector. Pair ERP materials in the same `category_raw` whose descriptions match after stripping the word `rugged` (case-insensitive). `MAT-10033` Passenger Counting Camera and `MAT-10034` Passenger Counting Camera Rugged must appear. Attach notes whose `object_reference` is `PASSCOUNT-CAMERA` or `PASSCOUNT-CAMERA-RUGGED` (`N-018`, `N-019`) as evidence. Do not assign them one component id.
- Also include existing `functional_similarity` reconciliation rows (door-controller style pairs) as candidates. They stay two entities.
- Every row has an `explanation` string that names the refs, the relationship, and the evidence ids. Build it from the row fields. Do not call an LLM.
</context>

<feature>
  <name>Already-reused and reusable-candidate reports</name>
  <files>app/services/analysis.py, tests/test_analysis.py</files>
  <behavior>
    `already_reused(conn)` returns a list of dicts:

    `entity_type`, `canonical_id`, `name`, `variant_refs` (sorted unique, length >= 2), `variant_count`, `source_bom_line_ids`, `explanation`.

    Cases:
    - One canonical component on two variants → one row, `variant_count` 2, explanation states it is the same canonical component on those variants.
    - A component on only one variant → omitted.
    - An unresolved pending-identity line that was not written to `bom_relationship` → omitted.
    - After the test accepts the identity cluster and calls `build_canonical_model` again, that component appears and the explanation mentions the accepted identity refs.
    - The same shape for an assembly present on two variants.

    `reusable_candidates(conn)` returns a list of dicts:

    `left_ref`, `right_ref`, `relationship` = `functional_similarity`, `review_needed` true, `evidence` (reconciliation id and/or note ids), `blocked_by` (list, may be empty), `explanation`.

    Cases:
    - A fixture `functional_similarity` reconciliation row for two different normalized refs appears once. It does not appear in `already_reused`.
    - A `variant_specific` reconciliation row does not appear.
    - ERP rows `MAT-10033` / description `Passenger Counting Camera` and `MAT-10034` / description `Passenger Counting Camera Rugged`, same category `COUNTING`, plus notes `N-018` and `N-019`, produce one candidate. `evidence` includes those note ids. `explanation` says qualification differs and the rows were not merged.
    - Two descriptions that differ by more than the word rugged (for example `HVAC Fan Standard` vs `HVAC Fan Nordic`) are not paired by this rule.
    - Candidates are ordered by left_ref, then right_ref.

    Call `build_canonical_model` inside the tests that need BOM links. Do not add CLI here.
  </behavior>
  <implementation>
    Read canonical BOM for reuse. Read `component_reconciliation.evidence_json` for similarity rows. Read `erp_material.description_raw` and `category_raw` for the rugged-description rule. Read `engineering_note` for note ids; match `object_reference` exactly to `PASSCOUNT-CAMERA` and `PASSCOUNT-CAMERA-RUGGED` for the camera pair, and also attach a note when its `object_reference` equals either candidate ref.

    Strip rugged with a single regex on the description (`\brugged\b`, case-insensitive) and compare the collapsed remainder. Do not add embeddings or an LLM.

    Do not write new identity reconciliation rows. The candidate list is a derived report.
  </implementation>
</feature>
