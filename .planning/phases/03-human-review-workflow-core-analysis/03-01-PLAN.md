<feature>
  <name>Reconciliation accept, reject, and redirect</name>
  <files>app/services/review.py, app/db/schema.py, tests/test_review.py</files>
  <behavior>
    `decide_reconciliation(conn, entity_type, reconciliation_id, action, rationale=None, redirect_source_id=None, decided_by="operator")` updates one row in `component_reconciliation`, `assembly_reconciliation`, or `supplier_reconciliation`.

    Cases:
    - accept on a PENDING identity row → status ACCEPTED, `decided_at` and `decided_by` set, rationale stored when provided, and `component_id` (or assembly_id / supplier_id) set to a new canonical row. A second accept of a cluster peer whose evidence members include the first source reuses that same canonical id. Return the updated row including canonical id.
    - accept on a PENDING `functional_similarity` row → status ACCEPTED and rationale stored, but `component_id` stays NULL. Do not create a shared component.
    - accept on a PENDING `variant_specific` row → status ACCEPTED and a new canonical component is created for that source only. It must not reuse the canonical id of a different normalized reference.
    - reject on PENDING → status REJECTED, rationale required (raise ValueError if missing), canonical id stays NULL.
    - redirect on PENDING → original row becomes REJECTED with rationale prefixed `redirected:`, and a new PENDING row is inserted with method MANUAL, canonical id NULL, and evidence containing `relationship` from the original (default `identity`), `redirect_from` (old id), `target_source_component_id`, and `review_needed: true`. Missing `redirect_source_id` raises ValueError.
    - decide on a row that is already ACCEPTED or REJECTED → raise ValueError. Do not overwrite.
    - unknown entity_type or action → raise ValueError.
    - calling `record_reconciliation()` for the decision is wrong: it will not update the existing row. Use UPDATE for the decision. INSERT only for the new redirect proposal.

    Schema created in this plan, idempotent `CREATE TABLE IF NOT EXISTS`, no FK from reconciliation tables back to these:
    - `component(id, name, category, normalized_reference, created_at)`
    - `assembly(id, name, category, normalized_reference, created_at)`
    - `supplier(id, name, country, normalized_reference, created_at)`
    - `variant(id, name, train_family, market, climate_class, capacity_class, voltage_system, normalized_reference, created_at)`
    - `bom_relationship(id, variant_id, assembly_id, component_id, quantity, unit, source_bom_line_id, created_at)` with UNIQUE(variant_id, assembly_id, component_id, source_bom_line_id)
    - `technical_fact(id, entity_type, entity_id, attribute, value, unit, source_type, source_id, confidence, status, created_at)` status OBSERVED/VALIDATED/CONFLICTING

    `init_database` must create these tables. Existing reconciliation tests must still pass.
  </behavior>
  <implementation>
    Add the tables in `app/db/schema.py` next to the reconciliation tables. Comment that FKs from reconciliation id columns stay omitted (SQLite cannot add them without a rebuild; Phase 2 left them off on purpose).

    Put decisions in `app/services/review.py`. Read `evidence_json` to branch on `relationship`. For identity accept, look for an ACCEPTED row whose source id is listed in this row's evidence members (the Phase 2 identity evidence lists other cluster members) and reuse its canonical id when present. Create the canonical `component`/`assembly`/`supplier` row otherwise, using the source entity's `normalized_reference` as name and normalized_reference.

    Do not run ingestion, do not call `run_full_reconciliation`, and do not write CLI commands in this plan.
  </implementation>
</feature>
